*从确定游戏创意、控制项目规模、选择引擎，到用视觉化方式搭建游戏、设计文档、制作低保真原型并收集反馈，最后设置 GitHub 版本控制，用占位素材推进开发。适合准备开始做第一款游戏的开发者参考。*

制作一整款电子游戏是极其艰巨的任务，无论你是独自开发还是与团队合作。这里面涉及很多东西，人们很容易忽略一些至关重要的初始步骤，而这些步骤可能决定了你游戏的后续成败。

你可能知道，我最近停止了一款开发了将近一年的游戏，开发后期出现的很多问题都是因为我严重缺乏准备。但在我开始开发新游戏时，我会尽我所能把这款游戏规划好，让它尽可能有条理。

所以跟我一起开始做我的游戏吧！我会教你开始游戏开发时应该做些什么，我会尽量让它互动性强又有趣，因为我知道这里面很多东西很容易被人忽视。

严格来说，开始做游戏时，这些步骤都不是必须的，但我强烈推荐，其中大部分其实是开发和设计领域的行业标准。所以希望你看完这期视频也能学到些新东西。

话不多说，我们开始吧！

首先，我们要确定创意，这个很简单。做游戏得知道做什么，而这一切都始于一个机制、故事或其他想法。我想如果你想做游戏，大概已经有想法了，所以这部分我不多讲。但如果你还没有想法或者想换个新点子，我发现两个最适合头脑风暴的地方：洗澡时和户外。说实话，任何让我站起来或活动的活动，总能让我思绪涌动。

不管怎样，一旦你有了可爱游戏的点子，就停下来仔细审视一下它：这个游戏有多大？你觉得做出来要花多长时间？把这个数字乘以 40。

但最重要的是，这是不是一个规模宏大的毕生之作？最好不是。如果这是你最初几款游戏之一，请确保整个想法都能写在一张便利贴上——所有功能、机制、故事，一切。

如果你非常坚持要做更大的游戏，那就先用“便利贴法”做试玩版，等试玩版全部完成后，再升级到用索引卡做更大的游戏，但仅此而已，不要超过这个界限。相信我，这会让你的游戏规模小很多，你就能相对快速地完成它。

另外，很多初学者卡住的另一个地方是游戏引擎。对此我的真诚建议是：你越早选定一个，就能越早开始做游戏。所以直接选一个，每个引擎几乎都能做所有事。你可以去研究一下，但说到底引擎并不重要，除非你要做电影级杰作，那你可以用虚幻 5。

好，现在游戏构思已经就绪，该开始规划了。

先从游戏设计文档入手，这大概是最重要的一份。不过咱们说真的，谁会看这个？现在没人读书了，更别说写。我一直是视觉型学习者，用 MLA 格式写一整篇关于我游戏的说明文，听起来极其无聊。我其实曾为第一个游戏写过游戏设计文档，但后来觉得无聊就没写完。

所以要是能有办法让这份本来无聊的文档看起来酷，做起来也有趣就好了。

幸运的是，多亏了本期视频的赞助商 MetaNote（你可能不知道这句话我想说多久了）。MetaNote 是一个在线画布，你可以在上面规划、头脑风暴，并为任何创意项目协作，包括游戏设计。他们甚至专门有游戏开发的模板，还有很多其他爱好的模板。

说实话，自从我第一款游戏的设计文档惨不忍睹之后，我就一直在看 MetaNote。我觉得它让整理游戏的每个部分变得容易多了。我能做的最好的比较是，它基本上是一本图画书，概述你想要的任何创意主题，而不是常规游戏设计文档那种学术论文的格式。

对于我的新游戏，我一直在搭建我的看板，并把它分成 4 个不同的部分：概念、关卡设计、角色设计，还有一个待办清单。如你所见，每个部分都有自己的看板，基本上就像是你想规划的每个主题的子文件夹。

那我们来过一遍我的几个看板，让你看看我目前是怎么把游戏搭建起来的：

1. 游戏参考：
我放了 6 款游戏，把它们各自放在一列里，配上图片，还有一小段说明为什么它是参考。它们大多是音游，但我觉得对我游戏想法最准确的描述是《CrossCode》和《Hi-Fi RUSH》的结合，再加上《宝可梦不可思议的迷宫》的 Roguelike 生成。

2. 关卡设计：
在试玩版里我只想要 3 个关卡：工厂、森林和火山。这些都是按顺序排列的，所以我用这些箭头表示它们，一个接一个。我还为每个关卡列了一份要实现的功能清单，这样制作时能更有方向。

至于额外的关卡，我这里拼贴了一堆不同的想法，比如一个漂浮在物体上的水关卡、一个洞穴，还有几个以后可能用上的。

我用 Milanote 的在线网页剪藏工具把这些直接加到我的画板里。这非常有用，因为我不需要费劲地保存、截图、重命名，再移动到合适的文件夹里。出于我的完美主义，最后再把它加进项目，这帮我省了好多时间。

3. 主要机制：
我放了动图，这样你能大致看出每个机制我想做成什么样：
(a) 移动与攻击：会有我们常见的行走和冲刺攻击，类似《CrossCode》，再加上节奏机制。
(b) 背包系统：会像《宝可梦不可思议的迷宫》，你能在地面捡到不同物品，然后选择吃掉或扔出去。
(c) 技能树：会有一个技能树用来打造一些独特的流派，我甚至在同一栏里列了一些升级点子的清单。

4. 主角设计：
我有这个看板，把参考图和美术素材都放在一起，还有一些我自己画的像素画，这样一切都能整齐地摆出来。以后我可能会在这些部分下面加一些背景故事，但现在先不加，因为大家都知道我上一个游戏出了什么事，最后是人，我有这些机器狗。

每个区域会有不同的攻击方式，但外观会很相似，这样就能省下做一大堆精灵图的时间。没错，它们来自之前那只狗，或者放松点。

为了把一切串起来，我这里有主待办清单，这样我就真能有个计划，知道要做什么。

做游戏时，待办清单超级重要。把它放在 Milanote 上真的很方便，尤其是你可以创建子任务，所以如果你的步骤像我的一样比较宽泛，就能写得更具体一些。

把所有想法、关卡和机制都规划好并整理在一个地方，实现游戏本身就会容易得多，因为你不用操心下一步做什么，也不会因为没计划而不断往清单里加新东西，卡在原地。

Milanote 让你轻松把所有东西集中在一处，无论是做游戏还是其他创作，规划规划，它们甚至还有手机应用能和桌面版同步，这样你在外面逛街时想到的新笔记或点子就不会忘掉。最棒的是它免费而且没有时间限制。所以如果你想自己建一个看板来写游戏设计文档或规划其他项目，就点我简介或置顶评论里的链接。总之，再次感谢 Milanote 赞助本期视频。

接下来进入做游戏的下一部分：原型制作与初始编码阶段。

在这个阶段，我们想确认的是点子好不好。

为此可以做一个原型，基本上就是用占位素材和很烂的美术做的试玩版，看看机制本身好不好玩，这样就能避免浪费时间做美术，或规划一个可能根本不好玩的游戏。

至于我的游戏，因为我打算做俯视角地牢探索，最终原型会有多层敌人，我也会展示我设想的战斗机制。

但还有一种原型做起来要简单得多。原型分为两种：低保真和高保真。

我上一款游戏直接做了高保真，把整个游戏功能做完之后再收集反馈。这是个大问题，因为已经花了几周甚至几个月在改东西，会多出大量工作，极其耗时。

把你的想法展示出来并获得极其严厉反馈的一个非常简单的方法，就是制作一个低保真原型。这是你的游戏玩法的一个画得极其糟糕的版本。它可以是在纸上画的草图，画出概念并加以解释，也可以是一段短动画，只展示游戏的精髓。既然它看起来已经很糟了，人们就不太可能对你手下留情，因为你基本上没投入多少精力去做它，这正是我们想要的。

让我给你看个例子。在我的游戏里，我很想加入节奏元素。主角是一只装了机械植入体的狗，踩准节拍能让植入体发挥得更好。我想给“踩拍攻击”一些奖励，所以我觉得加入节奏游戏元素会超级有趣。

比如，没踩准拍子的攻击就是普通攻击，跟一般的俯视角游戏一样；根据攻击模式的不同，如果你踩准了拍子，就能获得加成，给连击加点东西，或者触发特殊效果。

我还在琢磨这个，不过既然我给你们看了个做得超烂的原型，你们说它难看也不用不好意思。所以如果你们对节奏机制有什么想法，随时告诉我，但我不会只给你们看。为了说到做到、以身作则，我真的跑到外面，向我认识的最挑剔的人——我的朋友们，征求了对我原型的反馈。而且我确实把所有笔记都带在这儿了，上面记着我收到的全部反馈。没错，我不光画画像 5 岁小孩，我的字迹也毫不逊色。

在原型阶段，说实话，人越多越好，因为你能从不同角度看待你的想法，这要么帮你发现陷阱，要么让它变得更好。所以你看，制作原型并获取反馈是设计过程中超级重要的一环，你绝对应该考虑为你的游戏这么做。

现在你终于有了机制本身的扎实方案，是时候开始写代码了。既然我们做了设计文档，还给大家看了糟糕的原型，现在完全清楚想要什么，所以这应该挺简单的。

我们在这里加了个跳跃，然后……哦，我把它弄坏了。要是能有办法保存代码之前的状态，更有效地追踪游戏的变化，那就好了。

好吧，我们来聊聊版本控制。这个也非常重要，做游戏时，版本控制在很多情况下都能救命。版本控制基本上能帮你保存编码进度，而且你可以在各个存档之间来回切换，查看游戏的先前版本，或者干脆把它当作“逃生绳”，摆脱你陷入的任何灾难。它也很适合跟踪进度，如果你觉得自己什么都没做成，看看版本历史能帮你看到为了走到今天，你已经完成了哪些事。

现在你可能会问，这个神奇的功能要怎么设置？幸运的是，有现成的应用可以用。别担心，我们要用来追踪存档的工具是 GitHub。GitHub 基本上就是一个网站，很多人把代码放上去保存在代码仓库里。你可以把代码仓库想成存放所有存档的地方，这很棒，因为它能显示你所有改动的完整历史。如果你有团队，每个人都能设置好，非常轻松地一起做项目。我们用最简单的方式来设置：

1. 注册账号：首先你要注册一个 GitHub 账号，就在他们网站上注册。
2. 下载软件：接下来下载 GitHub Desktop，也在他们网站上下载。打开 GitHub Desktop 后，它看起来是这样的。
3. 准备游戏：开始之前，我们先打开 Godot，把游戏本身做出来（如果你已经有游戏了，可以跳过这部分）。
4. 登录软件：游戏建好后，我们回到 GitHub Desktop，点击左上角的选项，在这里登录 GitHub。它会提供一个外部链接让你在浏览器里登录，直接在那里登录就行。
5. 添加项目：登录后，我们点击“从本地驱动器添加现有代码仓库”，在这里找到你的游戏文件夹，把它选为代码仓库。如果找不到文件夹，打开 Godot 应用时它会按名称列出这些文件夹。
6. 创建仓库：选好文件夹后点击“添加代码仓库”，它会提示这不是一个 Git 代码仓库，因为确实不是，所以点击“创建代码仓库”链接就会带你到这里。这些就是代码仓库的所有选项。确保代码仓库的名称和你的游戏名称一致，以免之后要移动一堆文件。

至于许可证，大多数情况下你并不真的需要，但你随时可以之后再添加。

“.gitignore”文件有 Godot 的选项，这非常棒，他们也为其他引擎（比如 Unity 和虚幻）提供了选项。这个文件基本上会阻止不必要的文件被保存到代码仓库中。

7. 发布与提交：创建完代码仓库后，点击“发布代码仓库”的选项。现在你可以上 GitHub 查看代码仓库本身了，这里基本上就是用来查看随时间所做的所有更改的。

那我们实际改一下，你就能看到我的意思了。我现在在 Godot 里加了一张图片，放在了屏幕上。想保存关卡的话，我可以回到 GitHub Desktop，现在就能看到改动了。

在左下角你可以提交这些改动，这基本上就是创建一个存档。这次存档我叫它“added dog”，再写一小段描述，说明我做了什么。完成后，我可以点击提交到主分支，它就会在电脑上保存一个存档，但还没上传到 GitHub 上。要上传到 GitHub，我们只需要推送这些更改。幸运的是，GitHub Desktop 会提示你该怎么做。你可以照着屏幕上的指示操作，但提交几次后基本就成了肌肉记忆。

现在我们的提交已经在 GitHub 上了，我们可以看到所有更改的历史记录，过一段时间它会变得更丰富一些。

我其实可以给你看个例子，因为 Godot 就在 GitHub 上，它有 77000 次提交，这太夸张了！这是个开源项目，意思是任何人都能看到代码并帮忙更新它，但这还是太惊人了。

总之，这就是设置版本控制的方法。每当你做出改动，试着养成提交的习惯，你就能很好地记录游戏的更新历程。

版本控制非常重要，我真心希望你能考虑使用它。我上一款游戏只稍微用了一点，结果掉进了“只提交大更新”的坑里。凭经验我建议你别这么做，能提交的每个小改动都提交，尤其是和别人合作时。提交应该保持小规模，因为给巨大更新做存档状态可能会弄坏一堆其他东西，你也不想把提交信息写成莎士比亚式的长篇大作。

不过现在版本控制已经搭好了，我们其实可以开始写代码了，所以我现在不会深入讲编程教学，以后大概会把更深入的内容放到第二个频道。但我想讲一些通用准则，能帮你做第一款游戏：

首先，这个初始版本最好全是占位素材。具体到我的俯视角游戏，美术量比较大，有些精灵图集会有上百张，所以在我发布试玩版之前，我会用一堆占位素材。只有当我找不到某个机制或功能的占位素材时，我才会自己画美术，即便那样我也会故意把美术做得很差，免得自己花几个小时纠结它有多难看。

然后等到终于要发布试玩版的时候，我们有两个选择：要么用占位素材发布，前提是它们可以免费使用；要么像我一样用受版权保护的素材，那大概会让我在 Delfino Plaza 被判终身监禁。为了解决这个问题，我要做的是自己粗糙地把所有美术都做出来，然后发布那个“灾难版本”。但这没关系，你可以这样想：如果人们能接受糟糕的美术，那友好美术他们肯定更喜欢，对吧？

上个游戏里最耗时间的就是美术，我觉得用占位素材能大大加快进度。没错，当一切没做到我想要的样子时，我的完美主义让我内心崩溃，但我觉得这是个大家容易掉进去的大坑，包括我自己，我想不惜一切代价避免。

另外，代码组织也很关键。我在第 2 个频道回顾了上个游戏，连核心机制从哪开始到哪结束都找不到。我一直拿“没人会看我的代码”当借口，却没意识到“未来的我”也会存在，所以尽量好好整理。

外面有一些教程，讲状态机、容器化等等。说实话，这些术语听起来吓人，但它们其实只是整理代码的方法，学会基础后就不会忘。这个我还没试过，但听说评价特别好，很多人向我推荐过。

所以咱们来聊聊怎么找社区。说实话，虽然我大部分创作过程都是独来独往，但有时我完全搞不懂状况，只能去问别人。我最近发现，看教程、查资料的效果远远比不上直接跟一个真正懂行的人聊，而社区正是认识这种人的绝佳地方。在社区里，你有机会和经历相同的人交流，得到反馈，给出反馈，甚至交到新朋友。
