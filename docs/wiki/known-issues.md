# Known Issues and Technical Debt

Only issues that have been confirmed against the code are listed (checked at commit `3177f1d` plus the uncommitted story 009 changes, 2026-11-14). Paths omit the prefix `Game_01 5.8/Source/Game_01/`. Sorted by impact within each section. When you fix one, delete its entry.

## 1. Data and Save Game

### 1.1 The save version is checked only against 2 (partly fixed in story 008)
- **Location**: `SaveVersion` in [CampSaveGame.h](../../Game_01%205.8/Source/Game_01/Public/Flow/CampSaveGame.h), `Initialize` in [CampSaveSubsystem.cpp](../../Game_01%205.8/Source/Game_01/Private/Flow/CampSaveSubsystem.cpp) (line 43).
- **Status**: Story 008 added the check: a save with `SaveVersion < 2` has its `WarehouseRelics` migrated into `UnlockedOptions`, and `SaveNow` writes version 2. See [data-and-storage.md](data-and-storage.md#13-version-compatibility).
- **What is left**:
  - The load code has only that one branch. A file with a version above 2 (a newer game's save), or a later layout change that does not bump `CurrentSaveVersion`, is read as if it were version 2, and the next change rewrites it as version 2.
  - The class default of `SaveVersion` must stay 1 or old files will skip the migration (explained in the header comment).
  - The migration is one-way and lossy: `FReelUnlocks::OptionsForReels` skips reels whose row has no `UnlocksOption`; with the shipped data all three reel types now map (story 009), so nothing is dropped today, but a reel row with an empty option would be, and `WarehouseRelics` is never written back, so after the first v2 save they are gone for good.
  - If the slot exists but cannot be cast to `UCampSaveGame` (damaged file, changed class), `Initialize` logs a warning and starts a fresh camp; the next change then overwrites the slot (lines 65-68, 103-123).
  - Enums are stored by name (`ERelicType` in `WarehouseRelics`, `EBuildingType` as the keys of `BuildingLevels`). Renaming or removing an enumerator silently changes or drops old data; the enum names are therefore frozen (the `ERelicType` comment says so).
- **Suggestion**: When the layout changes again, bump `CurrentSaveVersion` and add the next migration branch; refuse or back up a file with a higher version.

### 1.2 A save is written several times per event, and an early write can be an intermediate state
- **Location**: [`UCampMetaSubsystem::TryUpgrade`](../../Game_01%205.8/Source/Game_01/Private/Camp/CampMetaSubsystem.cpp), [`UCampStockSubsystem`](../../Game_01%205.8/Source/Game_01/Private/Extraction/CampStockSubsystem.cpp), [`URunOutcomeSubsystem::EndRun`](../../Game_01%205.8/Source/Game_01/Private/Extraction/RunOutcomeSubsystem.cpp).
- **Symptom**: Every stock or building change triggers `SaveNow` through the listeners. An upgrade writes once after `SpendIron` (Iron deducted, level not yet raised) and again after the level goes up. A run settlement writes after `AddIron` (when it is more than 0), after each newly unlocked option, and once more explicitly (1 to 2+N writes for N new options); the first of them holds the new Iron without the unlocks.
- **Impact**: If the process is killed between two writes, the save holds an intermediate state ("Iron deducted, no upgrade"; "Iron banked, option not unlocked"). The window is tiny (within the same frame) but it exists; the file is rewritten needlessly.
- **Suggestion**: Finish changing all state first, then save once (for example suppress the listener during `EndRun` and `TryUpgrade`).

### 1.3 A missing data table or row falls back to C++ defaults silently
- **Location**: the `FindRow(..., false)` lookups in [EnemySpawnSubsystem.cpp](../../Game_01%205.8/Source/Game_01/Private/Enemies/EnemySpawnSubsystem.cpp) (34-55), [EnemyManagerSubsystem.cpp](../../Game_01%205.8/Source/Game_01/Private/Enemies/EnemyManagerSubsystem.cpp) (17-23), [HealthComponent.cpp](../../Game_01%205.8/Source/Game_01/Private/Combat/HealthComponent.cpp) (17-23), [RunProgressionSubsystem.cpp](../../Game_01%205.8/Source/Game_01/Private/Progression/RunProgressionSubsystem.cpp) (95-131), [CampMetaSubsystem.cpp](../../Game_01%205.8/Source/Game_01/Private/Camp/CampMetaSubsystem.cpp) (50-57), [FilmCardSubsystem.cpp](../../Game_01%205.8/Source/Game_01/Private/Editing/FilmCardSubsystem.cpp) (18-22), [LootConfig.cpp](../../Game_01%205.8/Source/Game_01/Private/Loot/LootConfig.cpp).
- **Symptom**: An unset table, or a row whose name is misspelled, keeps the C++ defaults without any log line; an unset film-card table means no cards at all. Only `ULootBagComponent::BeginPlay` logs where its numbers came from (`LOOTCFG source=table` or `source=c++ defaults`). In a packaged build the tables are soft references, which is why `DefaultGame.ini` has `DirectoriesToAlwaysCook=/Game/Data`; if that is lost the game still runs on defaults.
- **Impact**: Tuning edits can be silently ineffective, and nothing says so.
- **Loot-specific variants**: [`ULootConfig::FindContainerRow`](../../Game_01%205.8/Source/Game_01/Private/Loot/LootConfig.cpp) (102-130) uses the table rows if the table has any, with no per-type fallback: if `DT_LootContainers` has rows but none whose `ContainerType` field matches a container, `ALootContainer::Interact` logs a warning and returns false (LootContainer.cpp:70-74), so that container can never be searched. The lookup matches the row's `ContainerType` / `RelicType` field, not the row name, and takes the first match, so a mistyped field or a duplicate is silent too. `FindRelicRow` has the same first-match shape (it has no caller outside tests).
- **Suggestion**: Log a warning when a table is set but a row is missing, or the table is unset in a non-editor build.
- **Fixed in story 008 (note)**: the dismantle Iron (`RelicDismantleIron`) is gone with the dismantle action, and the loot numbers now come from three tables via [`ULootConfig::CreateFromSettings`](../../Game_01%205.8/Source/Game_01/Private/Loot/LootConfig.cpp). Not verified: the row values inside the `.uasset` tables, which cannot be read here.

### 1.4 The unlock loop has three leftovers
- **Location**: [`UCampStockSubsystem::IsOptionUnlocked`](../../Game_01%205.8/Source/Game_01/Public/Extraction/CampStockSubsystem.h) (no caller), [`FRelicRow::IsDroppable`](../../Game_01%205.8/Source/Game_01/Public/Loot/LootTypes.h), [`GenerateOffer`](../../Game_01%205.8/Source/Game_01/Private/Progression/RunProgressionSubsystem.cpp) (285-362).
- **Status**: Story 009 made unlocked options matter: the level-up pool and the reel drop rules read the unlocked set, and Chain, Haste and Magnet are real options. The old entry ("nothing reads the unlocked set") no longer applies.
- **What is left**:
  - `IsOptionUnlocked` still has no caller: the progression subsystem reads the whole list through `GetUnlockedOptions`.
  - Once all three options are unlocked, `PickRandomRelic` finds nothing droppable and no container can drop a reel, not even a vault with `RelicChance` 1.0. Carrying reels out earns nothing more after that.
  - The NEW marker is only taken by a first offer that actually shows three options. If the pool ever has fewer than three options, the auto-apply path returns before `TakeNewOptions()` and the markers stay for a later offer.

### 1.5 A table `MaxLevel` below 9 is ignored
- **Location**: [`URunProgressionSubsystem::MaxCopies`](../../Game_01%205.8/Source/Game_01/Public/Progression/RunProgressionSubsystem.h) (line 160), used in `GenerateOffer` and `ApplyOption`.
- **Symptom**: The copy cap is `max(row MaxLevel, CopiesForThreeStar)`. The defaults have `MaxLevel` 5 but the cap is 9, so lowering a weapon or passive `MaxLevel` in `DT_Weapons` / `DT_Passives` below 9 changes nothing.
- **Impact**: Misleading field; a designer cannot shorten an item's ladder.

### 1.6 Gameplay numbers still hardcoded in C++
The project rule is that values live in data ([master PRD section 5](../../design/prd/master-prd.md)), and `UDirectorTuningSettings` is described as holding "every gameplay number". Still in code:
- Boss XP is 10 times the normal gem: [RunProgressionSubsystem.cpp](../../Game_01%205.8/Source/Game_01/Private/Progression/RunProgressionSubsystem.cpp) line 263.
- Hero walk speed (600), interact range (250), camera distance and dodge (0.18 s, 1800 cm/s, 0.8 s cooldown, 0.25 s i-frames): [HeroCharacter.h](../../Game_01%205.8/Source/Game_01/Public/Player/HeroCharacter.h) 57-68. XP collect radius (80) and gem pull speed (900): [RunProgressionSubsystem.h](../../Game_01%205.8/Source/Game_01/Public/Progression/RunProgressionSubsystem.h) 183-187 (the magnet radius is data since story 009: `BaseMagnetRadius` in `DT_Progression`).
- Extraction time and reset rule are properties of the placed `AExtractionZone` ([ExtractionZone.h](../../Game_01%205.8/Source/Game_01/Public/Extraction/ExtractionZone.h) 33), so they live in the map, not in a table. Film-card slot count `MaxSlots = 2`: [FilmCardSubsystem.h](../../Game_01%205.8/Source/Game_01/Public/Editing/FilmCardSubsystem.h) 22.
- Building growth per level (0.5 of height) and all tint colors: [CampBuilding.cpp](../../Game_01%205.8/Source/Game_01/Private/Camp/CampBuilding.cpp) 55-59, [Enemy.cpp](../../Game_01%205.8/Source/Game_01/Private/Enemies/Enemy.cpp) 34-35.
- Display names: `FRelicRow::DisplayName`, `FLootContainerRow::DisplayName` and `FBuildingRow::DisplayName` are never read. The HUD and the toasts use the enum display names (`UMETA`), so editing the name in a table does nothing.

### 1.7 `project.yaml` still points at the warm-up project
- **Location**: `commands.build/test/run/smoke` (lines 59-62) and `engine.language` (line 35) in [project.yaml](../../project.yaml).
- **Symptom**: The project path in all four commands is `Game_Jam_01/Game_Jam_01.uproject`, and `engine.language` is `"Blueprint"`, while the actual project is `Game_01 5.8/` and C++.

## 2. Visuals

### 2.1 The hero, enemies and XP gems are gray, and tinting has no effect
- **Location**: [`AHeroCharacter::BeginPlay`](../../Game_01%205.8/Source/Game_01/Private/Player/HeroCharacter.cpp), [`AEnemy::Init`](../../Game_01%205.8/Source/Game_01/Private/Enemies/Enemy.cpp), [`AXpPickup::BeginPlay`](../../Game_01%205.8/Source/Game_01/Private/Progression/XpPickup.cpp).
- **Symptom**: These three places create a dynamic material on a cylinder or cube and set the `Color` parameter (the comments say "hero blue, enemy red, Boss purple, gem green"), but everything is gray. The evidence screenshot [1-reel-in-bag.png](../../production/qa/evidence/story-008-lost-film-reels/1-reel-in-bag.png) shows a gray hero and gray cubes.
- **Cause**: The mesh's default material has no `Color` parameter (the comment in `CampBuilding.cpp` says the cube defaults to `WorldGridMaterial`), so `SetVectorParameterValue` fails silently. The camp's [`ACampBuilding`](../../Game_01%205.8/Source/Game_01/Private/Camp/CampBuilding.cpp) and [`ACampWarehouse`](../../Game_01%205.8/Source/Game_01/Private/Camp/CampWarehouse.cpp) explicitly `SetMaterial` to `/Engine/BasicShapes/BasicShapeMaterial`, which does have `Color`, so they are tinted correctly (visible in the screenshots).
- **Suggestion**: In these three places, call `SetMaterial(0, BasicShapeMaterial)` before creating the dynamic material.

### 2.2 The camp message text does not disappear by itself
- **Location**: `Message` in [`UCampWidget`](../../Game_01%205.8/Source/Game_01/Private/UI/CampWidget.cpp).
- **Symptom**: The "Upgrade succeeded / Not enough Iron / Card added" line at the top of the panel stays until the next action.
- **Impact**: Cosmetic only. 3D clicks go through the expiring `UHudMessageSubsystem` messages.

## 4. Architecture and Robustness

- **Few automated tests**: There are 12 (4 star-tuning tests, 5 lost-reel tests since story 008 and 3 unlockable-option tests since story 009, under `Private/Tests/`). They cover only pure helpers (`FStarTuning`, `FReelUnlocks`, `FOptionUnlock`, the drop rules, the v1 migration helper); the unlock tests use a table of options written in the test, so nothing tests `GenerateOffer`, the NEW marker, the Chain path or the Haste and Magnet results against the real subsystem. The comment on [`FRunSettlement::Compute`](../../Game_01%205.8/Source/Game_01/Private/Extraction/ExtractionTypes.cpp) says "pure function, can be tested without opening the editor", but there is still no test for the settlement math, `CutOffer`, save load or building costs. Under `qa.level: minimal` tests are optional, so this is a permitted gap and not a violation.
- **No guard against "a world without a GameInstance"**: `GetWorld()->GetGameInstance()->GetSubsystem<...>()` dereferences null in an editor preview world. In story 007, `UFilmCardSubsystem::Initialize` crashed because of this once, and was changed to `UGameInstance::GetSubsystem<T>(GetWorld()->GetGameInstance())` (which returns null for null). The same old pattern remains in [`UAutoWeaponComponent::FireWeapon`](../../Game_01%205.8/Source/Game_01/Private/Combat/AutoWeaponComponent.cpp) (82), [`URunOutcomeSubsystem::EndRun`](../../Game_01%205.8/Source/Game_01/Private/Extraction/RunOutcomeSubsystem.cpp) (45, 62), [`ALootContainer::Interact`](../../Game_01%205.8/Source/Game_01/Private/Loot/LootContainer.cpp) (81), [`ACampBuilding`](../../Game_01%205.8/Source/Game_01/Private/Camp/CampBuilding.cpp) (35, 44) and the probes in `ADirectorGameMode`. They only execute while the game is running, so they are currently safe. When writing a new world subsystem, do not dereference the GameInstance directly in `Initialize`.
- **`EndRun` does not null-check the bag**: `URunOutcomeSubsystem::EndRun` calls `Bag->GetIronCount()` straight away (line 43). The two real callers (the zone and the hero) always pass a valid bag; a future caller that passes null will crash.
- **Progression binds to the enemy manager without declaring the dependency**: [`URunProgressionSubsystem::Initialize`](../../Game_01%205.8/Source/Game_01/Private/Progression/RunProgressionSubsystem.cpp) (133) gets `UEnemyManagerSubsystem` with `GetSubsystem<>` and no `Collection.InitializeDependency`, unlike `UFilmCardSubsystem` and the camp subsystems. If the manager were initialized later, the `OnEnemyKilled` binding would be skipped with no log and no XP gem would ever drop. It works today (the evidence screenshots show level-ups).
- **The auto-apply path of `GenerateOffer` does not re-check the level**: with fewer than three options left, the remaining options are applied and the function returns (RunProgressionSubsystem.cpp 327-334) without a further `CheckLevelUp`, so leftover XP that already covers the next level waits until the next gem. `CutOffer` does call it. Only reachable late in a run (most options maxed or cut).
- **Soft pause is not complete**: `AExtractionZone::Tick` ([ExtractionZone.cpp](../../Game_01%205.8/Source/Game_01/Private/Extraction/ExtractionZone.cpp) 102-138) does not check `IsOfferPending()`, so a player standing in the zone keeps filling the bar behind the level-up panel and can extract (the HUD hides the panel once the run is inactive). In `AHeroCharacter::Tick` ([HeroCharacter.cpp](../../Game_01%205.8/Source/Game_01/Private/Player/HeroCharacter.cpp) 253-258) the dodge branch does not test `CanAct()`: a dash in progress keeps moving the hero for up to its 0.18 s after the level-up panel opens, after death, or after the run ended.
- **The probes touch the real save and share timing**: `-ReelProbe` settles a real run, so it unlocks options (`Haste`, plus `Magnet` and `Chain` with `-ReelCount=2` or `3`), adds Iron and writes `CampSave` unless `-SaveSlot=Name` is also passed ([CampSaveSubsystem.cpp](../../Game_01%205.8/Source/Game_01/Private/Flow/CampSaveSubsystem.cpp) 12-21). It reads its start delay and step time from `OfferProbe` ([DirectorGameMode.cpp](../../Game_01%205.8/Source/Game_01/Private/Game/DirectorGameMode.cpp) 49), so changing those changes both probes. `-OfferProbe` and `-ReelProbe` both rely on the shipped `ADirectorGameMode` and must run on `L_Greybox`.
- **Hardcoded map names**: `L_Camp` and `L_Greybox` appear as strings in [CampWidget.cpp](../../Game_01%205.8/Source/Game_01/Private/UI/CampWidget.cpp) and [RunHudWidget.cpp](../../Game_01%205.8/Source/Game_01/Private/UI/RunHudWidget.cpp). Renaming them requires updating both.
- **Dependency cycles, unchecked**: see [dependencies.md](dependencies.md#1-how-modules-depend-on-each-other).
- **The `ModelContextProtocol`, `AllToolsets` and `Terminal` plugins are enabled for all targets** ([Game_01.uproject](../../Game_01%205.8/Game_01.uproject)): development tools will be carried into the package. Restrict them to Editor before release.
- **The camp panel is rebuilt wholesale**: when the state signature changes, it clears and rebuilds, and hover state is lost after a click. With a very long list (many unlocked options) it still relies on the scroll box.
- **Checked and fine**: every delegate handler bound with `AddDynamic` (`HandleDied`, `HandleMetaChanged`, `HandleRunEnded`, `HandleEnemyKilled`, `HandleCampChanged`, the zone overlaps, `HandleClicked`, both `HandleAction`) is a `UFUNCTION`.
